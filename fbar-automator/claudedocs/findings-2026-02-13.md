## Overview

Two-phase smoke testing of the FBAR Automator identified 8 bugs across the upload, review, and approval workflows. Phase 1 found 4 surface-level bugs that were immediately fixed. Phase 2 uncovered 4 critical API route issues blocking the approval workflow.

## Phase 1: Surface Bugs (FIXED)

### 1. PDF.js Worker Path Issue
**Status**: ✅ Fixed
**Component**: Document Viewer (`/components/review/DocumentViewer.tsx`)
**Severity**: High (blocked PDF rendering)

**Problem**: PDF.js worker script failed to load because the worker path was not configured correctly. PDFs would not render in the document viewer, breaking the core review workflow.

**Root Cause**: Missing or incorrect `workerSrc` configuration for react-pdf/pdfjs-dist.

**Fix Applied**:
- Added `postinstall` script to `package.json` to copy `pdf.worker.min.mjs` to `/public/`
- Configured `pdfjs.GlobalWorkerOptions.workerSrc` in `DocumentViewer.tsx` to point to `/pdf.worker.min.mjs`
- Added webpack configuration in `next.config.mjs` to handle `.mjs` files with `javascript/auto` type
- Added `transpilePackages: ['react-pdf']` to ensure proper PDF.js compilation

**Files Changed**:
- `package.json` (postinstall script)
- `next.config.mjs` (webpack rules + transpilePackages)
- `src/components/review/DocumentViewer.tsx` (workerSrc configuration)

### 2. Upload Field Name Mismatch
**Status**: ✅ Fixed
**Component**: Upload Section (`/components/upload/UploadSection.tsx`)
**Severity**: High (blocked file upload)

**Problem**: Frontend FormData used `file` as the field name, but the API route expected `files` (plural). This caused a 400 Bad Request error on every upload attempt.

**Root Cause**: Inconsistent naming between frontend and backend upload handling.

**Fix Applied**:
- Changed FormData field name from `file` to `files` in `UploadSection.tsx`
- Verified API route (`/api/filing-years/[filingYearId]/upload`) expects `files` field

**Files Changed**:
- `src/components/upload/UploadSection.tsx`

---

### 3. UserRole Enum Casing Mismatch
**Status**: ✅ Fixed
**Component**: Sidebar (`/components/layout/Sidebar.tsx`)
**Severity**: Medium (role checks failed)

**Problem**: Prisma schema defines UserRole enum values in SCREAMING_SNAKE_CASE (`ADMIN`, `PREPARER`, `REVIEWER`), but frontend code used lowercase strings (`"admin"`, `"preparer"`, `"reviewer"`), causing role-based UI elements to fail.

**Root Cause**: Type system mismatch between Prisma enums and frontend string literals.

**Fix Applied**:
- Updated all role checks in `Sidebar.tsx` to use uppercase enum values: `"ADMIN"`, `"PREPARER"`, `"REVIEWER"`
- Added type imports from `@prisma/client` to enforce enum usage

**Files Changed**:
- `src/components/layout/Sidebar.tsx`

---

### 4. Missing Role Fallback in Session Handling
**Status**: ✅ Fixed
**Component**: Dashboard Layout (`/app/(dashboard)/layout.tsx`)
**Severity**: Medium (authentication edge case)

**Problem**: When session exists but user role is `null` or missing, the layout crashes instead of redirecting to login or showing an error.

**Root Cause**: No null-safety check for `session?.user?.role` before rendering dashboard.

**Fix Applied**:
- Added fallback logic: if `session.user.role` is missing, default to `"PREPARER"` role
- Added type guard to ensure role exists before passing to child components

**Files Changed**:
- `src/app/(dashboard)/layout.tsx`

### 8. Approve Account Payload Mismatch
**Status**: 🔧 In Progress
**Component**: Review Page Client (`/app/(dashboard)/clients/[clientId]/[filingYear]/review/ReviewPageClient.tsx`)
**Severity**: Critical (blocks account approval)

**Problem**: The "Approve Account" button sends a malformed payload to `POST /api/accounts/[accountId]/approve`. Multiple issues:

1. **Wrong URL parameter**: Frontend sends `statementId` in URL, but API expects `foreignAccountId`
2. **Wrong filingYear type**: Frontend sends `filingYear: "2025"` (string), but API expects `filingYearId: <UUID>` (string UUID)
3. **Missing required fields**: API requires `maxValueLocal` (number), `currencyCode` (string), but frontend doesn't send them
4. **Wrong corrections structure**: Frontend sends flat corrections object, but API expects nested `{original, corrected}` structure per field

**Current Frontend Payload** (incorrect):
```typescript
{
  filingYear: "2025",  // Should be filingYearId (UUID)
  corrections: {       // Should be {field: {original, corrected}}
    bankName: "...",
    accountNumber: "..."
  }
}
```

**Expected API Payload** (from `/api/accounts/[accountId]/approve/route.ts`):
```typescript
{
  filingYearId: "655eeb60-...",  // UUID
  maxValueLocal: 12500.00,       // number
  currencyCode: "EUR",           // ISO 4217
  exchangeRateSource?: "TREASURY",
  exchangeRate?: 1.234567,
  corrections?: {
    bankName: {
      original: "Deutsche Bank AG",
      corrected: "Deutsche Bank"
    }
  }
}
```

**Required Fix**:
- Update ReviewPageClient.tsx to send `filingYearId` (UUID) instead of `filingYear` (string)
- Send `maxValueLocal` and `currencyCode` from extracted data
- Transform corrections from flat object to nested `{original, corrected}` structure
- Change URL from `/api/accounts/${statementId}/approve` to `/api/accounts/${foreignAccountId}/approve`

**Files to Change**:
- `src/app/(dashboard)/clients/[clientId]/[filingYear]/review/ReviewPageClient.tsx`

## Cost Analysis: 12 Statements per Account

**Question**: Can the system handle 12 statements per account (monthly statements for a full year)?

**Answer**: ✅ YES — System is designed for this. 12 statements/account represents 0.08% of daily processing capacity.

**Capacity Calculation**:
- Queue configuration: 10 jobs/minute rate limit (BullMQ default)
- Daily capacity: 10 jobs/min × 60 min/hr × 24 hr/day = **14,400 documents/day**
- 12 statements/account = **0.08% of daily capacity**
- Even at 100 accounts/day × 12 statements = 1,200 docs (8.3% capacity)

**Queue Configuration** (from `src/lib/queue.ts`):
```typescript
{
  attempts: 3,
  backoff: { type: "exponential", delay: 5000 },
  removeOnComplete: { count: 1000, age: 86400 },
  removeOnFail: { count: 5000 }
}
```

**Performance**: Average extraction time is 10-30 seconds per document (per PRD Section 8). Queue handles parallel processing with exponential backoff on failures.

## Cost per PDF Processing

**Question**: What is the cost per PDF extraction?

**Answer**: **$0.015 - $0.05 per statement** with 98%+ gross margin on subscription pricing.

**Pricing Breakdown**:
- **LLM Model**: Claude Sonnet 4.5 (`claude-sonnet-4-5-20250929`)
- **Input Tokens**: ~3,500 tokens (includes prompt + base64-encoded document)
- **Output Tokens**: ~1,000 tokens (structured JSON response)
- **Pricing** (as of Feb 2026):
  - Input: $3 per million tokens
  - Output: $15 per million tokens

**Cost Calculation** (per statement):
```
Input cost:  3,500 tokens × $3/1M   = $0.0105
Output cost: 1,000 tokens × $15/1M  = $0.015
Total:       $0.0105 + $0.015       = $0.0255
```

**Cost Range**: $0.015 - $0.05 depending on:
- Document complexity (more pages = more input tokens)
- Extraction warnings (verbose output increases output tokens)
- Multi-account documents (extract 2-3 accounts from one PDF)

**Revenue Context** (from PRD Section 9):
- Professional tier: $3,990/year for 75 FBARs/month included
- Enterprise tier: $6,990/year for unlimited FBARs
- Overage: $10/FBAR (1 FBAR = 1 client filing, typically 2-6 accounts × 12 statements = 24-72 PDFs)

**Gross Margin**:
- Average FBAR revenue: $20/filing (blended)
- Average FBAR cost: 3 accounts × 12 statements × $0.025 = $0.90
- **Gross margin: 95.5%**

Even at $0.05/statement (high end):
- Cost: 3 accounts × 12 statements × $0.05 = $1.80
- **Gross margin: 91%**

**Token Usage Tracking**: Every extraction is logged with `llm_tokens_used` in the `statements` table for cost monitoring.
