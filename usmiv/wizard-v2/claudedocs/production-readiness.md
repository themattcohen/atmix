### 1. SEO

**[P0] Title encoding bug: myers, myersGold, myersPlatinum pages**

`create-wp-pages.mjs` serialized the apostrophe in "Myers' Cocktail" as a backslash-escaped character when building the JSON POST body. The `_seopress_titles_title` meta field was stored as `Myers\` (six characters, truncated). All three Myers variant pages render `<title>Myers\</title>` in production HTML today.

Confirmed live via REST:
- `GET /wp-json/wp/v2/pages/11336` returns `meta._seopress_titles_title: "Myers\"`
- Same for `myersgold` and `myersplatinum` slugs.

`update-wp-pages.mjs` already contains the fix (its header comment says "fixes the Myers\\ encoding bug"). The script has NOT been run yet (no `live-test-report.md` exists). Running it will correct all three titles.

**[P1] Open Graph and Twitter Card tags missing on all 27 treatment pages and /find-my-treatment/**

Zero OG or Twitter Card meta tags appear on any sampled page (myers, hydration, semaglutide, nad500, labComplete, find-my-treatment). `create-wp-pages.mjs` writes only `_seopress_titles_title` and `_seopress_titles_desc` to the SEOPress meta fields. Social sharing tags (`_seopress_social_og_title`, `_seopress_social_og_desc`, `_seopress_social_og_img`, `_seopress_social_twitter_title`, etc.) are never set.

Result: any link shared to Facebook, Twitter, Slack, iMessage, or LinkedIn shows no preview image, generic title, and no description.

**[P1] `<title>` values are treatment names only, with no site/brand suffix**

Current titles: `Hydration IV`, `NAD+ IV (500mg)`, `Complete Wellness Panel`. The SEO sweet spot is 50-60 characters. Every treatment page title is 12-31 characters. None include a brand suffix like `- U.S. Mobile IV` or `- Mobile IV Therapy Denver, CO`.

Measured lengths:
| Page | Current title | Length |
|------|---------------|--------|
| hydration | Hydration IV | 12 |
| nad500 | NAD+ IV (500mg) | 15 |
| labComplete | Complete Wellness Panel | 23 |
| semaglutide | Semaglutide (GLP-1) Weight Loss | 31 |
| find-my-treatment | Find My Treatment - U.S. Mobile IV | 34 |

Target format: `<Treatment Name> - Mobile IV Therapy | U.S. Mobile IV` (50-60 chars). This requires updating `_seopress_titles_title` for all 27 pages.

**[P1] Canonical slug case mismatch: 12 treatment pages**

WordPress normalizes slugs to lowercase at page creation time. The config `pageUrl` values and sitemap still use camelCase for 12 treatments. The canonical tag on each page points to the lowercase URL. SEOPress registers the lowercase URL as the canonical, so Google will index the lowercase form.

Affected IDs: `myersGold`, `myersPlatinum`, `lipoShots`, `b12Shot`, `biotinShot`, `glutathioneShot`, `triImmuneShot`, `vitaminDShot`, `labGeneral`, `labInDepth`, `labVitamin`, `labComplete`.

Confirmed: `https://usmobileiv.com/treatments/myersGold/` canonical is `https://usmobileiv.com/treatments/myersgold/`. WP serves both URLs with a 200 (no redirect), so the camelCase URL works today, but see the runtime bug in bucket 2 below.

**[P2] find-my-treatment `<title>` at 34 characters**

`Find My Treatment - U.S. Mobile IV` is readable but short for the primary conversion page. Consider `Find My IV Treatment | U.S. Mobile IV - Denver, CO` (51 chars).

### 2. Schema Markup

**[P1] No MedicalProcedure / Service / Product schema on any treatment page**

All 27 treatment pages emit one JSON-LD block: a `BreadcrumbList`. There is no `MedicalProcedure`, `MedicalTherapy`, `Service`, or `Product` schema. For a medical services site these are the primary structured data types that enable rich results in Google Search and AI overview citation.

Minimum recommended schema per page:
- `Service` (or `MedicalProcedure`) with `name`, `description`, `offers.price`, `offers.priceCurrency`, `provider` (Organization), `areaServed`.
- `BreadcrumbList` is already present (good).

**[P2] No Organization or LocalBusiness schema sitewide**

No `Organization` or `LocalBusiness` JSON-LD was found in the site `<head>` or on the homepage. For a local medical services business this is a P2: name, address, phone, geo coordinates, and opening hours should be declared once globally.

### 3. AEO (Answer Engine Optimization)

**[P1] /llms.txt exists but /llms-full.txt returns 404**

`https://usmobileiv.com/llms.txt` returns HTTP 200 and lists recent treatment pages. `https://usmobileiv.com/llms-full.txt` returns HTTP 404. LLM crawlers (Perplexity, ChatGPT plugin, Claude.ai) preferentially consume `llms-full.txt` for deeper content. With only the stub file present, AI overview coverage is limited to page titles and descriptions rather than full treatment content.

The current `llms.txt` content is auto-generated by SEOPress (likely its sitemap-mirroring feature) and covers recent pages but does not include treatment ingredient lists, clinical rationale, or pricing -- the structured content that enables AI citation.

**[P2] FAQ-style extractable content is present via inline JS but not in static HTML**

The treatment renderer (inline `<script>` on every page) builds section headings like `Why This Works`, `Who This Is For`, and `What to Expect`. These sections contain the `whyMatch` and `bestFor` content that is ideal for AI overview citation. However, this content is rendered by JavaScript after page load. It is not present in the static HTML that crawlers (including AI crawlers) parse. Googlebot renders JS, but most AI summary crawlers do not. The static page body is a bare `<div class="treatment-detail">` shell.

No AnswerSEO plugin is installed.

### 4. Accessibility

**[P1] Three H1 elements per treatment page (before JS runs)**

The static HTML of every treatment page contains three `<h1>` elements:

1. The WP-rendered H1 from the Bricks template: `Myers' Cocktail` (correct)
2. `' + esc(treatment.name) + '` -- a JavaScript template literal inside an inline `<script>` block that regex-based tools and some crawlers misidentify as an H1 (the string is inside a JS string, not live DOM, but the `<script>` block is not properly isolated from naive heading extraction)
3. `Treatment Not Found` -- a fallback H1 inside the inline renderer's error branch

In the actual rendered DOM, only the first H1 is live. However, screen readers that parse source-order headings before JS executes may announce all three. The `Treatment Not Found` H1 appearing in source before JS hydration is a confusing accessibility state.

**[P2] Two `<img>` tags without `alt` attribute on treatment pages**

Two tracking pixel `<img>` tags from Facebook Pixel lack `alt` attributes:
```
<img height="1" width="1" style="display:none" src="https://www.facebook.com/tr?id=1124790669539738...">
<img height="1" width="1" style="display:none" src="https://www.facebook.com/tr?id=1445783157196118...">
```
These should have `alt=""` (empty alt for decorative/tracking images). One additional `<img>` has an empty alt attribute (acceptable for decorative images).

**[P2] Heading level skip: H1 to H3 inside the treatment page**

The heading order in myers: H1 (treatment name) -> H2 (Why This Works) -> H3 (Eligibility Criteria) -> H2 (Who This Is For) -> H2 (What to Expect) -> H2 (Program Information) -> H3 (Dosing Schedule) -> H3 (Side Effects) -> H2 (Related Treatments) -> H3 (Services, in footer). The structure is H1->H2->H3 without skips, which is acceptable. No critical heading order violations detected in the sampled page.

### 5. Content (em-dashes and style rule compliance)

**[P1] treatment-sync.js emits `&mdash;` between ingredient name and benefit**

`wordpress/treatment-sync.js` line 75:
```javascript
if (ing.benefit) html += ' &mdash; ' + escapeHtml(ing.benefit);
```

This renders every ingredient line as `B12 &mdash; Energy and neurological support` in the live DOM. `&mdash;` is an HTML entity for an em-dash (U+2014). The project rule (`feedback_no_em_dashes.md`) prohibits em-dashes in user-facing copy. Every treatment page with ingredients (all IV, NAD, and injection pages) emits em-dashes between ingredient name and benefit text.

The fix is to replace ` &mdash; ` with ` -- ` or `: ` in treatment-sync.js line 75, and redeploy the plugin asset.

**[P2] Double-hyphen ` -- ` used as em-dash substitute in iv.ts (altitude treatment)**

`src/data/catalog/iv.ts`, in the `altitude` treatment's `addressedBy` object:
```
'High-altitude air is extremely dry -- this IV replaces fluid your body loses faster at elevation'
```
The double-hyphen is a typographic stand-in for an em-dash and should be rephrased to avoid any dash-as-separator construction. Suggested: `High-altitude air is extremely dry; this IV replaces fluid your body loses faster at elevation.`

No em-dashes (U+2014) or `&mdash;` appear in any catalog `.ts` files. The double-hyphen in `altitude` is the only instance in source data. The runtime emission via treatment-sync.js is the systemic issue.

### 7. WP Rocket Configuration

**[P1] Config REST endpoint emits incorrect Cache-Control header**

`GET https://usmobileiv.com/wp-json/wizard-of-iv/v1/config` returns:
```
Cache-Control: public, max-age=0, s-maxage=2592000
```

The migration plan specifies `Cache-Control: no-cache` for this endpoint. `s-maxage=2592000` is 30 days of shared-cache TTL. Cloudflare is currently bypassing this (`cf-cache-status: DYNAMIC`), likely because Cloudflare's default page rules bypass `/wp-json/*`. However, if a third-party CDN, reverse proxy, or aggressive browser cache honors `s-maxage`, it would serve a stale 46KB config blob for up to 30 days after a price or content change. The wizard's admin save-and-publish cycle would silently not propagate.

Fix: in `wizard-of-iv.php`, the GET route callback must set `header('Cache-Control: no-store, no-cache, must-revalidate')` explicitly before returning the response.

**WP Rocket script deferral: no action needed**

WP Rocket "Delay JS" is NOT deferring `treatment-sync.js` or `wizard.js`. Both scripts load as normal `<script src="...">` tags with no `data-rocketlazyloadscript` or deferred type markers. The scripts execute synchronously on page load. No WP Rocket exclusion configuration changes are needed for current behavior.

**WP Rocket page cache: no action needed for correctness**

Treatment pages (`/treatments/myers/`) are served from Cloudflare cache (`CF-Cache-Status: HIT`). Cache-Control is `public, max-age=0, s-maxage=2592000`. The treatment pages contain only static Bricks-rendered content. Dynamic content (price, name, ingredients) is injected by `treatment-sync.js` fetching the config at runtime -- the page HTML itself does not need to be cache-busted when config changes. No "Never Cache URLs" rule is needed for `/treatments/*/`.

The `?nocache=1` bypass confirms the pages render identically with or without cache, verifying correct separation of static HTML and dynamic JS hydration.
