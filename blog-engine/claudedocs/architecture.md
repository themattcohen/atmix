## 3. Pipeline Steps

### Step Definitions (`pipeline.STEPS`)

| Index | Name | Label | Icon |
|-------|------|-------|------|
| 0 | `nlp_input` | Keywords & Surfer NLP Targets | Target |
| 1 | `research` | Research Brief | Books |
| 2 | `write` | Write Article | Writing |
| 3 | `review` | Review & Iterate | Loop |

### State Machine

Each step progresses through these statuses:

```
pending -> running -> review -> approved
                        |
                        v
                     (edit mode -- stays in review)
                        |
                        v
                      redo -> pending (restart step)
```

**Run-level status**: `active` or `completed`.

A run transitions to `completed` when `advance_step()` is called on the last step (index 3). The `advance_step()` function increments `current_step` by 1 and sets `status = "completed"` if `new_step >= len(STEPS)`.

### Step Advancement Flow

1. User completes a step (status becomes `approved`).
2. Main area shows "Advance to [next step]" button.
3. Button calls `pipeline.advance_step(run_id)` which increments `current_step` in DB.
4. For step 2 (Write), "Continue to Review" auto-advances without a separate button.
5. For step 3 (Review), "Approve Final" calls `advance_step()` which sets run status to `completed`.

### Reopen for Editing

Completed runs can be reopened via "Reopen for Editing" button, which:
- Sets run status back to `active`
- Sets `current_step` to the currently viewed step
- Sets that step's status to `review`

## 4. Database Schema

### `runs` Table

| Column | Type | Default | Description |
|--------|------|---------|-------------|
| `id` | TEXT PK | UUID hex | Pipeline run identifier |
| `config_name` | TEXT NOT NULL | -- | Config JSON filename (e.g., `ofcpa.json`) |
| `keyword` | TEXT NOT NULL | -- | Primary target keyword |
| `slug` | TEXT NOT NULL | -- | URL slug derived from keyword |
| `secondary_keywords` | TEXT | `'[]'` | JSON array of secondary keywords |
| `current_step` | INTEGER | 0 | Index of the active pipeline step (0-3) |
| `status` | TEXT | `'active'` | `active` or `completed` |
| `created_at` | TEXT | -- | ISO 8601 UTC timestamp |
| `updated_at` | TEXT | -- | ISO 8601 UTC timestamp |

### `steps` Table

| Column | Type | Default | Description |
|--------|------|---------|-------------|
| `id` | TEXT PK | UUID hex | Step record identifier |
| `run_id` | TEXT NOT NULL | -- | FK to `runs.id` |
| `step_index` | INTEGER NOT NULL | -- | Step number (0-3) |
| `step_name` | TEXT NOT NULL | -- | Step name (`nlp_input`, `research`, `write`, `review`) |
| `status` | TEXT | `'pending'` | `pending`, `running`, `review`, `approved`, `failed` |
| `output_json` | TEXT | NULL | JSON blob storing step-specific output data |
| `screenshots` | TEXT | NULL | JSON array of screenshot file paths |
| `user_notes` | TEXT | NULL | User-provided notes |
| `started_at` | TEXT | NULL | ISO 8601 UTC timestamp |
| `completed_at` | TEXT | NULL | ISO 8601 UTC timestamp |
| `error` | TEXT | NULL | Error message if step failed (added by migration) |

**Index**: `idx_steps_run` on `(run_id, step_index)`.

**Migrations** (applied in `init_db()`):
- `ALTER TABLE runs ADD COLUMN secondary_keywords TEXT DEFAULT '[]'`
- `ALTER TABLE steps ADD COLUMN error TEXT`

When a run is created via `create_run()`, 4 step rows are pre-inserted (one per `STEP_NAMES` entry) with status `pending`.

## 7. Data Flow

### Step 0: NLP Input

**Inputs**: Surfer screenshots (entities, headings), pasted entity text, AI SEO facts text/screenshot.

**Processing**:
1. Pasted text (Slot 3) parsed via `nlp_parser.extract_from_text()` (Claude).
2. Screenshot (Slot 1) processed via `ocr_parser.extract_with_ocr()` (Tesseract -> regex -> Claude verify).
3. Terms merged across sources (highest `targetMax`, lowest `targetMin` on collision).
4. Categorized into `high_priority` / `medium_priority` / `low_priority` by `targetMax` (>=5 high, >=2 medium, else low).
5. Sanity checks run (K-notation misreads, range inversions).
6. AI vision verification against source screenshot.
7. Headings (Slot 2) processed separately; all heading targets forced to `targetMin=1, targetMax=1`.
8. AI SEO facts (Slot 4) from text or screenshot.

**Outputs**:
- `output/<slug>/surfer-targets.json` -- approved NLP targets
- `output/<slug>/crosslinks.json` -- discovered blog articles (optional, from cross-link discovery)
- Step `output_json`: `{nlp_targets, term_count, call_info, ai_facts}`

### Step 1: Research Brief

**Inputs**: Keyword, secondary keywords, niche config.

**Processing**:
1. Claude generates research brief with system prompt for SEO research analyst.
2. Authority domains and primary sources from config injected into prompt.
3. `check_brief_completeness()` verifies 5 expected sections: Key Facts, Competitor Gaps, Unique Angles, Authority Sources, Recommended Article Structure.
4. If sections missing, auto-complete via `writer.rewrite_with_feedback()` with targeted feedback.
5. Re-checks completeness after auto-complete.

**Outputs**:
- `output/<slug>/research-brief.md`
- Step `output_json`: `{brief, brief_file, call_info, completeness, complete_call_info}`

### Step 2: Write Article

**Inputs**: Keyword, research brief (from disk), NLP targets (from disk), config, crosslinks (from disk), secondary keywords.

**Processing**:
1. Claude writes full MDX article with `writer-guide.md` + `anti-slop-rules.json` in system prompt.
2. NLP targets formatted with mandatory enforcement language (high = non-negotiable, medium >= 70%, low = best effort).
3. Crosslinks loaded from `crosslinks.json` (or falls back to config crosslinks).
4. **Auto-optimization loop**: `auto_review.analyze_article_against_targets()` runs locally (zero cost), then `gap_analysis.build_surfer_feedback()` generates structured feedback, then `writer.rewrite_with_feedback()` rewrites if gaps found.
5. Local validation via `scorer.run_local_validation()` (Node.js subprocess).
6. Article converted to HTML via `scorer.md_to_html()` for Surfer paste.

**Outputs**:
- `output/<slug>/article.mdx`
- Step `output_json`: `{article, article_file, validation, call_info, opt_call_info, auto_review}`

### Step 3: Review & Iterate

**Inputs**: Article (from disk), user feedback, Surfer screenshots.

**Processing** (iterative loop):
1. Article rendered as copyable HTML for pasting into Surfer Content Editor.
2. User uploads up to 4 Surfer screenshots: Score Overview, Entities Panel, Headings Panel, AI Optimization.
3. Each screenshot parsed by dedicated `nlp_parser.extract_*()` functions.
4. `gap_analysis.build_surfer_feedback()` generates structured feedback text.
5. Feedback pre-populated into text area (also persisted to DB as `draft_feedback`).
6. User can edit feedback, then trigger rewrite via `writer.rewrite_with_feedback()`.
7. New article version written to disk. Iteration counter incremented. Feedback history preserved.
8. Hero image generation via `imagen.generate_hero_images()` (3 candidates, user selects one).
9. Final approval via "Approve Final" marks step approved and completes the run.

**Outputs**:
- `output/<slug>/article.mdx` (updated each rewrite)
- `output/<slug>/hero.webp` (final hero image)
- Step `output_json`: `{iteration, history, cost_history, analysis_cost_history, hero_options, hero_selected, hero_cost, draft_feedback}`

## 8. Recent Features (as of 2026-03-05)

### Research Brief Self-Healing

After initial generation, `check_brief_completeness()` scans for 5 required sections. If any are missing (or the last section is truncated with <10 words), the system automatically calls `writer.rewrite_with_feedback()` with a targeted prompt listing the missing sections. A second completeness check runs after auto-complete; any remaining gaps are surfaced as a warning.

### Run Navigation

- `st.session_state.viewed_step` allows viewing any past step while a run is active.
- Sidebar renders clickable step buttons for completed/past steps.
- Completed runs default to showing the last step (Review).
- "Reopen for Editing" button on completed runs sets the run back to `active` and the selected step back to `review` status.

### Screenshot-Based Surfer Gap Analysis

Step 3 accepts 4 screenshot panel types:
1. **Score Overview** -- parsed by `extract_score_overview()` for score, word count, headings, paragraphs, entity coverage, AI facts.
2. **Entities Panel** -- parsed by `extract_entities_with_counts()` for entity term current vs. target counts.
3. **Headings Panel** -- parsed by `extract_heading_counts()` for heading term presence.
4. **AI Optimization** -- parsed by `extract_ai_optimization()` for fact coverage status.

All parsed data feeds into `build_surfer_feedback()` which generates structured feedback with specific gap counts and "ADD N+ uses" directives per entity.

### Auto-Optimization Loop in Step 2

After initial article generation, the system:
1. Runs `analyze_article_against_targets()` locally (zero API cost) -- counts word frequency, heading presence, AI fact coverage.
2. Feeds results into `build_surfer_feedback()` to generate structured feedback.
3. If gaps are detected, automatically calls `writer.rewrite_with_feedback()` with the structured feedback.
4. Saves the optimized version to disk.

### Hero Image Generation

Uses Google Imagen 4 (`imagen-4.0-generate-001`):
- Generates 3 candidate images per request.
- Each image: 16:9 aspect ratio, resized to 1200x630, saved as WebP (quality 85).
- Prompt built from article title + description + config `heroImage.imageryMap` regex matching.
- User selects one; chosen image copied to `hero.webp`, other options deleted.
- Cost: $0.02 per image ($0.06 for 3 candidates).
- Async execution via persistent event loop in `ui/components.py`.

### Internal Crosslink Discovery

In Step 0 (NLP Input), users can trigger crosslink discovery:
1. `scrape_blog_index()` fetches the blog index page.
2. Extracts article links + titles via 3 strategies: article containers, main content, all links (fallback).
3. Filters out non-article paths (about, contact, category, tag, etc.).
4. `fetch_article_summary()` fetches each article and extracts first meaningful paragraph.
5. Saves to `output/<slug>/crosslinks.json`.
6. Writing step loads crosslinks and includes them in the Claude prompt as available internal links.

## 10. Cost Tracking

### Pricing Tables (`lib/costs.py`)

**Claude Sonnet 4.6**:
- Input: $3.00 / 1M tokens
- Output: $15.00 / 1M tokens
- Cache write: $3.75 / 1M tokens
- Cache read: $0.30 / 1M tokens

**Imagen 4**:
- $0.02 per image generated

### call_info Schema

Every API call returns a `call_info` dict. Two formats:

**Claude call_info**:
```json
{
  "model": "claude-sonnet-4-6",
  "input_tokens": 1234,
  "output_tokens": 2456,
  "cache_write_tokens": 0,
  "cache_read_tokens": 0,
  "cost_usd": 0.042,
  "call_name": "write_article",
  "latency_s": 12.5,
  "continuations": 0,
  "truncated": false
}
```

**Imagen call_info**:
```json
{
  "model": "imagen-4.0-generate-001",
  "images_requested": 3,
  "images_generated": 3,
  "cost_usd": 0.06,
  "call_name": "generate_hero_images",
  "latency_s": 8.2
}
```

### Cost Flow

1. **Generation**: Each API call in `writer.py`, `nlp_parser.py`, `imagen.py` computes a `call_info` via `calc_claude_cost()` or `calc_imagen_cost()`.
2. **Step Storage**: `call_info` is stored in the step's `output_json` under known keys:
   - Step 0: `call_info` (aggregate of all extraction costs)
   - Step 1: `call_info` (generation), `complete_call_info` (auto-complete, if triggered)
   - Step 2: `call_info` (write), `opt_call_info` (auto-optimization, if triggered)
   - Step 3: `cost_history` (list of rewrite call_infos), `analysis_cost_history` (list of screenshot analysis call_infos), `hero_cost` (Imagen call_info)
3. **Sidebar Summary**: `_build_cost_sidebar()` in `app.py` reads all steps' `output_json`, extracts costs, and displays per-step + total cost in the sidebar "Run Costs" expander.

### Typical Cost Per Run

| Step | Operation | Approximate Cost |
|------|-----------|-----------------|
| Step 0 | NLP extraction (text parse) | $0.01-0.03 |
| Step 0 | OCR + Claude verify | $0.06-0.10 |
| Step 1 | Research brief generation | $0.05-0.10 |
| Step 1 | Auto-complete (if needed) | $0.05-0.10 |
| Step 2 | Article writing | $0.15-0.25 |
| Step 2 | Auto-optimization | $0.10-0.20 |
| Step 3 | Screenshot analysis (per batch) | $0.05-0.10 |
| Step 3 | Rewrite (per iteration) | $0.10-0.20 |
| Step 3 | Hero images (3 candidates) | $0.06 |
| **Total** | **Typical full run** | **$0.50-1.20** |

## 11. CLI Runner (`run_cli.py`)

A headless alternative to the Streamlit UI. Shares the same DB, config, and output directories.

### Usage

```bash
python3 run_cli.py <run_id> <step> [options]
```

### Commands

| Step | Arguments | Description |
|------|-----------|-------------|
| `nlp-input` | `[path/to/surfer-targets.json]` | Load NLP targets from file |
| `research` | (none) | Generate research brief |
| `write` | (none) | Write article |
| `review` | `"feedback text"` | Rewrite article with feedback |
| `image` | `[--count N]` | Generate hero image options |
| `image-select` | `N` | Select hero image by number |
| `status` | (none) | Show current run state + output files |

The CLI auto-advances steps after completion (except `review`, which stays in `review` status for iterative feedback).
